# ISP Management Platform

A Splynx-inspired ISP management platform: customer CRM, billing/invoicing,
network device & IP address management, a customer self-service portal, and
support ticketing — built with **Django + DRF** (backend) and **React + Vite
+ Tailwind** (frontend).

> **Scope note:** Splynx is a mature commercial product built over many
> years by a dedicated team. This project is a solid, working foundation
> covering the four modules requested — real data models, authentication,
> role-based APIs, and functional UIs for both staff and customers — not a
> line-for-line feature match. See "What's simulated" below for the one
> area that's mocked rather than fully real.

Looking to put this on a live server? See **[DEPLOYMENT.md](./DEPLOYMENT.md)**
for Docker Compose and bare-metal VPS instructions.

## Stack

- **Backend:** Django 5, Django REST Framework, Simple JWT, PostgreSQL, django-filter, Gunicorn, WhiteNoise
- **Frontend:** React 19 + TypeScript, Vite, Tailwind CSS v4, React Router, Recharts, Axios

## Modules

1. **Customer CRM** — customer records, contact details, status/category, balance, assigned staff.
2. **Billing** — tariffs/plans, customer services (subscriptions), invoices with line items, payments, auto-calculated totals/tax.
3. **Network management** — device inventory (routers/switches/OLTs/APs), IP address pools & assignment, per-device monitoring charts (bandwidth, latency).
4. **Customer self-service portal** — customers log in to see their plan, invoices, payment history, and raise/reply to support tickets.
5. **Support ticketing** — tickets with department/priority/status, threaded comments, internal-only staff notes.

## Project layout

```
isp-platform/

```

## Getting started

### 1. Backend

```bash
cd backend
python3 -m venv ../venv && source ../venv/bin/activate
pip install -r requirements.txt   # or see the package list below

# Create a Postgres database matching backend/.env (defaults: ispplatform / postgres / postgres)
createdb ispplatform

cp .env.example .env   # adjust DB credentials if needed
python manage.py migrate
python manage.py seed_demo_data          # creates staff, customers, tariffs, invoices, tickets…
python manage.py simulate_monitoring --hours 48 --interval-minutes 15
python manage.py runserver 0.0.0.0:8000
```

Packages used (install with `pip install`): `django djangorestframework
djangorestframework-simplejwt django-cors-headers psycopg2-binary
python-decouple django-filter`

### 2. Frontend

```bash
cd frontend
npm install
npm run dev     # http://localhost:5173, proxies /api to http://localhost:8000
```

Staff/admin users land on `/admin`; customers land on `/portal`. The API
enforces this at the data layer too — a customer JWT can only ever read
their own invoices/services/tickets, never the customer list or network
devices (verified with 403s during testing).

## What's simulated vs. real

Everything is real except **network monitoring readings**. There's no
physical network to poll in this environment, so `network.MonitoringReading`
rows are generated by `python manage.py simulate_monitoring`, which writes
realistic-looking latency/bandwidth/CPU data per device on a timer.

To wire in real SNMP polling later:
1. Install an SNMP client (e.g. `pysnmp`, or shell out to `snmpget`/`snmpwalk`).
2. In a new scheduled task (cron/Celery beat), for each `Device`, poll
   `device.ip_address` using `device.snmp_community` / `device.snmp_version`
   for standard OIDs (`ifInOctets`/`ifOutOctets` for bandwidth, `sysUpTime`
   for uptime, `hrProcessorLoad` for CPU) and write the results into
   `MonitoringReading` — the model and API/UI already expect exactly that
   shape, so nothing downstream needs to change.
3. Run it every 1–5 minutes instead of the one-off demo command.

Everything else — customers, billing math (subtotal/tax/total, payment
application to invoices and customer balance), IP pool assignment, ticket
threads with internal-note visibility rules, and role-based API scoping —
is fully functional against a real PostgreSQL database, not mocked.

## Extending this further

Natural next steps, roughly in priority order: password reset / customer
self-signup, recurring invoice generation (a scheduled job that creates next
month's invoice per active service), email/SMS notifications, a reseller/
partner layer, richer network topology (parent/child device relationships,
outage detection from consecutive `is_up=False` readings), and a proper
production deployment (Gunicorn/Nginx, environment-based settings, Docker
Compose for Postgres + backend + frontend).
